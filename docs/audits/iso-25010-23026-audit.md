# Audit ISO/IEC 25010 & ISO/IEC/IEEE 23026 — Pondok

**Tanggal**: 17 Oktober 2026
**Auditor**: Claude Code
**Repositori**: `pondok/pondok`
**Cakupan**: Audit kualitas perangkat lunak (ISO/IEC 25010) dan pengelolaan website (ISO/IEC/IEEE 23026) terhadap aplikasi Laravel 13 + Filament 5, difokuskan ke empat hal yang diminta: **kecepatan web, kemudahan navigasi, minim bug, dan kemudahan perawatan**. Audit dilakukan dari kode, konfigurasi, log, dan dokumentasi di repo — bukan pengukuran kinerja produksi secara langsung.

Dokumen ini sengaja ditulis **dua lapis**:

- **Bagian A** — ringkasan untuk orang awam (operator sekolah, reviewer non-teknis).
- **Bagian B** — detail teknis dengan bukti (path file + nomor baris) untuk developer.

# Bagian A — Ringkasan Bahasa Sederhana

## Apa yang diperiksa?

Saya memeriksa empat hal yang Anda sebutkan, lalu memetakannya ke dua standar internasional:

| Kebutuhan Anda | Standar yang dipakai |
|---|---|
| Kecepatan web | ISO 25010 — *Performance Efficiency* |
| Kemudahan navigasi | ISO 25010 — *Usability* + ISO 23026 — desain & struktur situs |
| Minim bug | ISO 25010 — *Reliability* & *Functional Suitability* |
| Kemudahan perawatan | ISO 25010 — *Maintainability* + ISO 23026 — pengelolaan siklus hidup situs |

## Hasilnya: Bagus

**Tidak ada temuan kritis.** Secara keseluruhan aplikasi Pondok sudah dirancang dengan disiplin yang jarang ditemui di aplikasi sekolah open source, dan banyak hal yang biasanya jadi sumber masalah justru sudah dicegah lewat desain dan test otomatis.

Yang sudah **baik** dan bisa dijadikan bukti tertulis:

- **Kecepatan**: hampir semua tabel admin sudah memuat data relasi sekaligus (menghindari ratusan query kecil), indeks database sudah dipasang di kolom yang sering dicari, dan halaman publik di-cache browser (300 detik) dengan aset yang ramping.
- **Navigasi**: semua menu admin (36 item) terkelompok, terurut, dan berlabel konsisten dalam Bahasa Indonesia; halaman publik punya menu yang sama di ponsel dan desktop, plus tombol "langsung ke isi".
- **Minim bug**: transaksi uang dilindungi transaksi database + penguncian + kunci unik agar tidak dobel; ada lebih dari 4.000 test otomatis yang memeriksa hak akses, tarif, tagihan, pembayaran, dan alur PSB.
- **Perawatan**: kode dibagi rapi per modul dengan aturan "satu operasi satu file", dokumentasi lengkap (panduan produk, skema database, panduan desain, cara pasang, cara rilis), dan ada pemeriksaan kesehatan server (`pondok:doctor`).

## Hal yang perlu diperbaiki

Dikelompokkan supaya aman dikerjakan bertahap. Tidak ada yang darurat.

**Grup 1 — Paling aman (cukup ubah pengaturan/dokumentasi/tampilan):**

1. Tambahkan pemeriksaan gaya kode otomatis (`Pint`) di alur CI agar kode tetap rapi.
2. Tambahkan *breadcrumb* (penunjuk lokasi halaman) di berita/galeri untuk membantu orientasi.
3. Samakan beberapa ikon menu admin dengan panduan desain.
4. Beri teks alternatif yang lebih bermakna pada gambar sampul kartu berita/galeri.

**Grup 2 — Perlu perubahan kecil di kode/database (tetap aman, cukup teliti):**

5. Tambahkan indeks database untuk laporan tunggakan (kolom `due_on`, `period`, `entered_on`).
6. Pindahkan operasi berat (buat tagihan manual & ekspor CSV) ke antrean agar halaman tidak macet saat data banyak.
7. Tambahkan pembersih berkala untuk berkas bukti transfer yang "yatim" (terunggah tapi transaksinya gagal).
8. Pisahkan file terjemahan `lang/id` yang sudah sangat besar agar lebih mudah dirawat.

**Grup 3 — Perlu uji lebih dulu:**

9. Uji konversi dua pendaftar jadi santri secara bersamaan di MySQL (saat ini baru diuji di SQLite).

# Bagian B — Detail Teknis

## Metode

Audit dilakukan dengan menelusuri empat area secara paralel: (1) kinerja, (2) navigasi/usability, (3) keandalan/minim bug, (4) maintainability & siklus hidup website. Setiap temuan disertai bukti path + nomor baris. Log aplikasi juga diperiksa untuk membedakan error produksi dengan log test.

**Stack terkonfirmasi**: PHP 8.3 (target produksi cPanel), Laravel 13.36, Filament 5.10 (admin), Blade + Livewire + Tailwind 4 + Vite 8 (publik), MySQL/MariaDB, `spatie/laravel-permission` + `filament-shield`, `spatie/laravel-activitylog`, Pest. Detail di `composer.json` dan `package.json`.

**Catatan log**: seluruh entri log yang ditemukan berada di channel `testing` (hasil menjalankan test suite), bukan produksi. Warning "tarif belum diatur" dan error "nomor tagihan bentrok" adalah skenario test yang memang sengaja diuji — bukan kegagalan produksi.

## Daftar rekomendasi (dikelompokkan berdasarkan risiko)

### Risiko rendah — aman dikerjakan lebih dulu

1. Tambah langkah `vendor/bin/pint --test` di `.github/workflows/tests.yml` agar gaya kode terjaga otomatis.
2. Tambah breadcrumb di `resources/views/portal/**` (berita/galeri/halaman statis).
3. Samakan ikon Filament dengan `docs/design-guide.md §3`.
4. Beri `alt` bermakna pada `post-card.blade.php:12` dan `album-card.blade.php:9`.
5. Pisahkan `lang/id/pondok.php` per domain (mis. `portal.php`, `psb.php`) bila ukurannya dirasa mengganggu.

### Risiko menengah — perubahan kode/database yang tetap terkendali

6. Tambah indeks: `invoices(status, due_on)` atau `(period, status)`, dan `students(entered_on)`.
7. Pindahkan generate tagihan manual (`InvoiceResource.php:292-296`) dan ekspor CSV (`ExportFinanceReportCsv.php`) ke queued job.
8. Tambah pembersih berkala untuk `payment-proofs` yang tidak memiliki `Payment` (kompensasi `RecordPayment.php:61`).
9. Pertimbangkan cache aplikasi persisten untuk agregat dashboard admin (saat ini dihitung ulang tiap request).

### Risiko lebih tinggi — perlu verifikasi/pengujian dulu

10. Uji konversi PSB bersamaan di MySQL (bukan hanya SQLite) untuk memastikan lock/unique bekerja seperti yang diharapkan.
11. Konsolidasi validasi ke FormRequest/DTO hanya bila API layer benar-benar ditambahkan (saat ini belum perlu — YAGNI).

## Kesimpulan teknis

Pondok lulus audit ISO 25010 + ISO 23026 dengan baik pada keempat area yang diminta. Fondasi terkuatnya ada di **keandalan jalur uang** (transaksi + idempotensi + audit + test) dan **dokumentasi/struktur yang membuat perawatan mudah**. Celah yang tersisa bersifat penyempurnaan, bukan kerusakan — dan sebagian besar bisa ditutup dengan perubahan kecil yang aman (config/tampilan) sebelum menyentuh kode yang lebih dalam.
